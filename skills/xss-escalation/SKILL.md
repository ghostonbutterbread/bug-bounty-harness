# XSS Impact Escalation

Load through `impact-escalation` after the initial finding is captured. `xss` and its selected lane own the source/sink, execution, delivery, and consumer proof; this overlay supplies **impact ideas**, not payload recipes, a mandatory checklist, or testing authority. Start with the observed executing origin, victim principal/role, how the victim reaches the content, frame/sandbox restrictions, and what that browser context can actually do. A self-only proof does not become cross-user impact without a delivery path. Revisit the app's normal UI, API operations, auth flows, and targeted MapStore gadgets as evidence appears. Generate novel paths from this application beyond the prompts below.

## Ideas: capability → application question

- **Act for the victim:** Can the browser perform meaningful actions—change security settings, invite an attacker-owned account, change membership/roles, export an owned artifact, or initiate a privileged workflow? Which role and tenant do they affect? Read back the actual authorized resource and final state; an API request or UI success message is not the effect.
- **Change account recovery or login:** Is there a primary, secondary, or recovery email/phone; a password change; a reset initiation; an MFA/passkey/device setting? Map both UI and underlying/alternate API flows. Old-password, OTP, recent-login, and mailbox-confirmation prompts are *claimed* prerequisites: load `assumption-testing` to test server enforcement and final account binding with owned accounts. One enforcing endpoint does not settle another route. Do not guess codes, access non-owned mailboxes, or claim bypass from client behavior alone.
- **Mint durable access:** Does the application issue an API key, personal token, OAuth grant, device session, invite-backed membership, or other reusable capability in this victim context? Determine whether the result is obtainable by the executing context and independently usable by an attacker-owned test principal/session, while preserving secrets only in approved restricted evidence. Distinguish creating a credential from merely making an authenticated request; never copy a live value into the ledger or report.
- **Session and data exposure:** Can execution read browser-accessible tokens, application data, or responses to same-origin authenticated requests? `HttpOnly` blocks JavaScript reads of that cookie value, not necessarily authenticated actions using it. Do not claim cookie theft without an actual readable cookie, nor full account takeover from a session-bound action. Explore whether a sensitive response is accessible in the actual origin and role, then retain only permitted minimal proof.
- **Reach and privilege:** Can a shared object, notification, email, preview, report, or staff workflow deliver execution to another owned role? Is that consumer same-origin and unsandboxed? A claimed admin audience, persistence, or a callback alone is not proof of admin-context execution. Route later consumers through `xss-lifecycle` and the relevant XSS lane.

For each promising path, pass the claimed gate to `assumption-testing`, account identity/recovery questions to `ato` or `password-reset`, object/role boundaries to `access-control` or `idor-live-policy`, and actual browser/API traffic through the inherited live controller and applicable account/Attempts policies. Test under owned fixtures and program constraints. Keep the strongest demonstrated effect and exact negative boundary in the same FID's evidence. Stop before non-owned account changes, unapproved mail delivery, secret collection, brute-force/OTP guessing, disruptive public/staff-visible payloads, or irreversible actions merely to decorate impact. Return the chain-link handoff specified by `impact-escalation`; `bunny-report-and-triage` remains report-only by default.
