# Program-scoped authenticated browser clone pool

**Status:** implementation specification; fixture-only checkpoint on `feat/browser-auth-policy-fixture-integration` (fetched base `origin/beta` `d077b89`, target `beta`; no production activation). The prior `feat/browser-auth-clone-pool` implementation began at `4998839`; the combined branch retains its history.
**Owner:** BBH browser provisioner and canonical profile lease. This supersedes the assumption that an automatically allocated Blue slot is already authenticated; it does not supersede the existing one-browser restricted policy or managed browser lifecycle.

## User contract

An agent requests a program and account/color (for example, Neon/Blue), not a slot or another program's Blue. The pool key is the resolved `(program, auth domain, account alias)`; color is an inventory mapping, never a global namespace. Each concurrent grant is a separate Chrome process, physical profile directory, lease, task proxy, and owner. Grants within the pool share a **verified authenticated baseline** where supported, rather than an empty profile. They never share a writable Chrome user-data directory. Agents in different programs can request Blue independently, subject only to node-wide capacity and their own program policy.

The provisioner exposes a program-level `single`/`multiple` setting that authorized agents can update with non-secret evidence after observing session behavior. A confirmed program-wide single-session rule restricts every account in that program to one effective browser; a narrower account/domain `single` rule remains restrictive under a program-wide `multiple` setting. Missing program policy retains existing behavior, but lack of clone readiness never yields an `authenticated` grant. Setting a policy changes future admissions only; it does not kill or deauthenticate existing owners. A passive logout report is evidence, not automatic classification: correlate the second login with the first session invalidation before switching to `single`.

## Auth-state source and transfer

1. Resolve the exact program/domain/account and a manager-owned source with a verified authenticated check. The source owner, unit, root, control generation, profile identity and authentication generation must match atomically at the transfer boundary. Do not attach an agent to another owner's raw CDP endpoint or rotate/freeze the source merely to read auth.
2. For an explicitly supported origin set and a session policy permitting export, use privileged node-local browser APIs to transfer the allowed cookies and origin localStorage into a new isolated profile. Payloads stay in restricted process memory or mode-0600 short-lived node-local IPC, never argv, stdout, logs, Git, proxy flow, lease DB, or public receipts. The destination gets its own proxy and CA; source proxy/CA material is never cloned. Filter unrelated origins and browser data.
3. A quiescent full-profile snapshot is an alternative for browser-bound or otherwise unsupported stores **only** after the source is positively terminal: exact unit/root/CDP closed, profile lock absent, filesystem identity stable. Publish an immutable private snapshot generation atomically; exclude runtime locks/sockets/proxy CA and verify the clone in a disposable destination before using it. Never copy a live Chrome directory, even with a filesystem-level best-effort copy. A snapshot may still be invalidated server-side.
4. Publish a clone as authenticated only after a program-specific browser-native authenticated check succeeds in that destination. Cookies/localStorage counts or a launched Chrome are insufficient. Unsupported IndexedDB, service-worker, sessionStorage, passkey/device-bound or server-bound login returns a typed `auth-clone-unavailable` / `needs-auth` result or queues the exact account; never silently substitutes a different account or labels an empty profile Blue-authenticated.

The source owner is not interrupted by cloning. Failed import/verification removes only the new disposable clone after exact root/CDP teardown; the source and other peers are unchanged. At the fixture transfer boundary, the manager derives a fresh private transaction identifier, exact owner lease, and recorded public CDP generation for each adapter before `/transfer/begin`; replay of that identical begin returns the same exclusive ticket, never a new one. An applied begin with a lost reply is recovered by one bounded identical replay, then explicitly ended (source) or aborted (empty destination). All private transfer calls and releases require the matching ticket, transaction, owner, and original generation. A second failed recovery checks exact adapter identity/availability; if exclusivity cannot be disproved, return `source-cleanup-incomplete` or `destination-cleanup-incomplete`, never claim a usable source or switch to another owner's ticket. A verified source release preserves its original public URL (not its old websocket epoch); a destination's old URL is rotated only on successful commit and remains closed through quarantine. Promotion's source-only native probe uses the same exact manager-derived begin/replay/end binding; a lost end reply, failed app evaluation, or cancellation still triggers exact end and an independent exact adapter identity/availability readback. If release is not proved, promotion publishes no generation and returns `source-cleanup-incomplete` (or propagates cancellation with a sanitized incomplete disposition), never claims the source usable. Direct fixture transfer is an initial empty-recipient clone primitive; it cannot consume an existing peer-ledger reservation. Running-peer update requires the separately authenticated recipient apply admission, which has no real caller-auth channel yet and therefore remains disabled. Release still ends only the requesting agent's browser/proxy. A new snapshot or auth generation is never inferred from file mtime alone.

## Auth updates and generations

A verified owner may explicitly promote its clone's auth to a new generation for its exact pool key. Promotion binds source identity, observed app auth check, allowed origins and generation; it cannot contain raw secret values in the record. Stopped peers consume the new generation on next launch. Running peers receive a pending update and apply it only at an owner-approved idle/restart boundary via their own privileged adapter, followed by their own auth check. Never overwrite active profile files, navigate another agent's tabs silently, or claim immediate synchronized login. If a program invalidates other sessions, record evidence and switch to `single`; do not loop automatic retries.

## Data and release safety

The old auto-slot migration grants physically isolated but potentially **unauthenticated** instances; distinguish those from verified clones in status and never promote them as shared-login success. Historical malformed Hoster manager rows remain quarantine; a partial repair or expired lease does not authorize copying the active Blue profile. No live Hoster Blue source is used for development tests.

Acceptance requires deterministic program/domain/color isolation, policy precedence and readback, two-request race, source/recipient identity and generation races, positive and negative supported-origin transfer, no secret in public artifacts, rollback and exact cleanup, single-session restriction, and promotion/update behavior. A disposable two-Chrome fixture must verify controlled canary login in both separate directories and a safe update to a peer, while the source stays live. The site-qualified check and unsupported-store refusal are explicit tests. Independent review and integrated beta tests precede publication; destination Hoster fixture, owner/data preflight and a separate activation decision precede live Blue use. A startup failure before CDP is not a clone proof; keep the existing deadline and sandbox.
