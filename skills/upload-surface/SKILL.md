# Upload Surface

This is a **surface router**, not an upload-bypass checklist. An accepted file is not an RCE or XSS finding. The security result depends on which component interprets which controlled value, in which context and privilege, and whether a downstream user or worker can reach it. OWASP separates malicious files, public retrieval, parser risk, overwrite, and resource exhaustion; PortSwigger distinguishes upload acceptance from subsequent execution or retrieval.[1][2]

For avatars/profile photos, `/pfp` coordinates the profile, crop, URL-import, and render workflow, then hands the observed file-byte, filename, metadata, processor, storage, or retrieval question here. Other uploads can start here directly; neither skill is a universal prerequisite for the other.

## Before acting

- For a live program, load `general-security-testing-policy`, `program-testing-policy` (including the program-specific rules), `live-testing-policy`, and `resource-safety-policy`; confirm scope, ownership, and safe cleanup. **Before even a baseline upload**, classify whether it, a support/moderation queue, notification, or retrieval will be public/staff-visible. If uncertain, follow `public-forums`' minimal classification and approval boundary before submission; if applicable, acquire its lease and plan verified cleanup. Use `browser-session-policy` → `chromium-test` to learn the normal UI flow, `attempt-recording-policy` for deliberate mutations, and `account-testing-policy` for owned fixtures. Do not let this router override those owners.
- Get a valid normal upload and its request/response, resulting object reference, processing state, storage/retrieval URL, and delete behavior. Record whether upload goes through app server, presigned object storage, resumable/chunked API, or third-party processor. Distinguish displayed original filename from actual stored object key.
- Prefer a harmless marker and minimal benign files. No web shells, destructive archive bombs, public malware, third-party data, or staff-triggered callbacks as exploratory defaults. If a class needs active payloads, load its live/injection policy first. OWASP recommends multiple independent controls rather than trusting MIME headers, extensions, or magic bytes alone.[1]

## Trace the file lifecycle

For each material entry point, make a short lineage packet:

`producer and owner → controlled components (bytes / extension / multipart Content-Type / filename / metadata / archive entries / URL / object key) → validator and canonicalization order → storage location and ACL → transformer or delayed worker → reference and retrieval response → browser/server consumer → cleanup`.

Include original versus derived artifacts (thumbnail, crop, OCR, transcript, extracted contents, PDF, export, email), raw response versus rendered view, and any change in content type, disposition, origin, permissions, or access token. Observe both upload-time and retrieval-time behavior. The Uppy HackerOne report attributed the SVG issue to the affected site's internal systems rather than Uppy itself: name the actual failing trust boundary, not merely the first UI touched.[3]

## Mechanism map and routes

- **Filename, title, description, EXIF/XMP, document properties, OCR text, extracted archive entry, or object key reaches a browser.** Track the marker through gallery cards, editor, activity feed, notifications, moderation/support, exports, emails, and downloads. Classify the actual output context and encoding, then route to `xss` → `xss-lifecycle` → `stored-xss`, `reflected-xss`, `dom-xss`, or `blind-xss` according to the observed consumer. Do not call a metadata value executable merely because it persists. OWASP identifies filename-based client-side risk; public HackerOne reports illustrate crafted SVG browser execution and filename XSS.[1][3][27]
- **Active content returned as a file:** SVG, HTML, XML, PDF/document viewers, or other browser-interpreted content may execute when served inline or embedded, depending on content type, disposition, origin, CSP/sandbox, and navigation context. Route to `xss` and the relevant browser/render subskill; compare raw headers with actual browser behavior. A rendered image preview and top-level navigation are not equivalent.[2][3]
- **Server-side code execution via file type or write location:** distinguish allowlist/extension/MIME/magic-byte bypass from the necessary *execution* prerequisite: web-server handler mapping, writable executable path, interpreter/include, dynamic plugin/config load, or a later conversion step. Route mapped leads to `rce-exploration` → `rce-surface-mapping`; observed primitives to `rce-validation` or `rce-lifecycle`. Never infer RCE from a PHP-looking string inside an image alone. In Sonar's osClass case, EXIF-held PHP needed a separate file-inclusion and administrator-session chain.[5] In its WordPress case, image-edit metadata and destination path were central.[4]
- **Filename/path/key traversal, collision, overwrite, or unsafe extraction:** compare original name with sanitized name, filesystem/object key, and derived-file destination; distinguish direct upload write from archive-entry extraction and thumbnail/crop output. A write outside the intended location is not necessarily execution. Route normalization/traversal to `injection-testing-policy`/`bypass`, read/include consequences to `lfi`, cross-owner objects to `access-control`/`idor`, and `rce-exploration` only when an execution consumer exists. Archives can carry traversal entries that overwrite files when extracted; image editing can create a second write sink.[4][6]
- **Parser and converter hazards:** map actual libraries, versions, handlers, options, worker identity, and whether metadata is *read*, transformed, or discarded. Candidate families include image/video transcoding, EXIF/XMP, XML/SVG, PDF/Office, OCR, AV/CDR, and archive extraction. Route parser-command/template/deserialization leads to `rce-technology-research`/`rce-validation`, external-resource fetching to `ssrf`, XML entity/file-read consequences to `lfi` or `information-disclosure-policy`, and nondestructive library-advisory analysis to `vulnerability-patch-research`. TwelveMonkeys' XMP parser had an XXE advisory; an ExifTool advisory documents hostile metadata leading to code execution—neither establishes that a target runs that component.[7][8]
- **Remote fetches during processing:** SVG/XML/PDF/media/document references, remote-import URLs, and fallback fetching can reach network or local resources; distinguish browser requests from server/worker requests. Route to `ssrf`, `lfi`, or `information-disclosure-policy` on concrete evidence, not merely a format's theoretical capability. An image editor's fallback retrieval featured in the WordPress chain.[4]
- **Authorization and exposure:** test only owned objects across upload initiation, part submission, finalization, media-record association, replacement, processing-job status, generated derivative, original download, private/public link, delete, and expired share. A signed upload URL, chunk upload ID, media ID, object reference and retrieval URL can each have different owner and lifetime checks; preserve which identity minted and which identity used each reference. Presigned upload permission and download permission may be separate. Route object ownership to `idor` + `idor-live-policy`; broader role/tenant permission to `access-control`; lifecycle/visibility rules to `business-logic-modeling` or `business-logic`. A grant for an owned object is not permission to probe the storage provider broadly. Do not fetch non-owned files to prove a hypothesis; use controlled pairs and minimal proof.
- **Stored references and later caches:** a client-controlled stored `path`, file ID, derivative key, or object reference may be used by a later read/delete worker, even when original bytes and filename are safe. Compare permission to set that metadata with permission to access the referenced resource; route the actual read/include sink to `lfi` or the cross-owner operation to `access-control`/`idor`. For a private attachment, origin authorization is distinct from a shared-cache response after permissions change: compare only owned fixtures, cache partitioning, response headers, and revocation without broad cache probing.
- **Resource consumption and lifecycle races:** size/count/quota, decompression, image dimensions, CPU-heavy conversion, retries, orphaned parts/derivatives, temporary-file windows, dedupe, and delete/replace ordering. Route race hypotheses to `race` + `race-live-policy`; quota and workflow abuse to `business-logic`. No high-volume upload, decompression bomb, or availability-impact test without the controlling policy and explicit program allowance. OWASP and PortSwigger both call out storage/DoS consequences.[1][2]
- **Parser identity and validation-to-use differentials:** determine whether eligibility uses a file signature/dimensions while a later converter selects a handler from the client filename, temporary-file suffix, or derived filename. Check whether a validated descriptor is reused or a mutable path is reopened after optimization; coder and external delegate policies can be separate. These are recognition questions, not a license for a live parser exploit or timing race. Route matched stacks to `rce-technology-research`/`vulnerability-patch-research`, a genuinely reachable state change to `race`, and any demonstrated file-read/write effect to its owning class.
- **XML documents and active exports:** if SVG, PDF/XFA, Office or other XML-derived bytes reach an entity-capable parser, route the actual outbound/file-read effect to `ssrf`/`information-disclosure-policy`; if CSV/spreadsheet cells later become formulas in a client export, route the import/export consumer through `injection-testing-policy`/`business-logic`. Treat accepted content without a reachable consumer as a lead. Upload/init/finalize requests authorized by ambient browser credentials may also raise a distinct `csrf` question.
- **Untrusted text fed into an AI processor:** OCR/transcription/document text or metadata may become model context rather than browser HTML. Route to `indirect-injection`/`ai-tester`; if the model may issue tool actions or publish results, add `agent-tool-abuse`/`ai-action-chain`. A prompt-injection hypothesis is separate from XSS in the same file.

## Discriminating questions

1. What precise attacker-controlled bytes or fields survive, and in what representation? Does server-side rename/re-encode remove them? Are originals retained separately?
2. Does validation occur on original, decoded, normalized, or derived form? Is the declared MIME type merely client input? Are filename, extension, signature, decoded content, and selected parser consistent?[1][2]
3. Which later consumer reads the value—browser render, server interpreter, media parser, archive extractor, AI worker, search index, admin UI, or external CDN? What principal and origin does it use?
4. Is processing synchronous, queued, retrying, or triggered by a later read/edit/export? Does the app expose a derivative different from the original?
5. What is the **minimal safe observation** that distinguishes acceptance, persistence, exposure, interpretation, and execution? Record each separately.

## Evidence and closure

Report a packet of `(normal upload, controlled field and marker, original→stored/derived transformation, exact consumer/trigger, raw response or browser observation, ownership, impact prerequisite, cleanup, next specialist)`. Separate observed fact from suspected path. When a class route takes over, do not duplicate its payload playbook here. A surface is covered only when material upload paths and discovered consumers have an observation, an explicit inapplicability reason, or an evidence gap/reopening condition. Keep unresolved candidates in the hypothesis ledger, not as findings.

The citations used here resolve in [Public upload cases](references/public-cases.md). Read that appendix only when a matched stack or mechanism needs an example; the case is not proof of a flaw in the current target.
