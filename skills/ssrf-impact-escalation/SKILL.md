# SSRF Impact Escalation

Load through `impact-escalation` **after** the initial finding has an FID. `ssrf` and its matching reference/technique pack own fetch confirmation, URL/parser/filter behavior, metadata and protocol mechanics; this overlay supplies *impact questions*, not payload recipes, a mandatory endpoint list, or permission to scan or use exposed credentials. A public callback alone is a fetch signal, not a demonstrated internal security boundary: keep testing under `ssrf` until there is a captured finding to escalate. Start with the actual fetcher: method, headers, redirects, body, authentication context, async behavior, output sink, and the network principal it appears to use. Reuse targeted MapStore gadgets and observed app architecture rather than a generic internal address sweep. Develop additional chains from this application beyond these prompts.

## Stack clue → reachable capability → observable effect

- **Discover the likely environment:** Use current app/API behavior, response headers and errors, worker/import design, service names in owned artifacts, documentation, permitted recon, and existing MapStore clues to form a small, ranked set of *hypotheses*. A cloud logo, hostname, framework header, or public DNS record does not establish the fetcher's runtime location, network access, or privileges. Where the app reveals multiple workers or routes, do not transfer an observation from one fetcher to another without proof.
- **Cloud or container metadata:** If evidence points to AWS, ask whether the reachable fetcher can satisfy the *actual* EC2 instance metadata service (IMDS) flow, as distinct from ECS task metadata or other credential sources. AWS IMDSv2 requires a token acquisition request and subsequent token header; a GET-only arbitrary-URL fetch does not imply this ability. For GCP and Azure, check whether the fetcher can send their required metadata headers and any route-specific version parameters. Kubernetes/container service identities are different questions again. Route mechanics to `ssrf`'s `metadata-scheme` pack and `headers`. Prove reach, response visibility, and the *kind* of data separately. Minimal credential exposure proof is not authorization to use a credential.
- **Internal application actions:** Which app-specific service/API, admin workflow, debug endpoint, queue, registry, or callback is suggested by the observed stack and roles? Can the fetcher cross a network or service-identity boundary the attacker cannot? Determine whether it can only GET, can send the required headers/body/method, or merely triggers an outbound request. For a proposed write, identify the exact owned target and independent read-back of changed state; route guards and claimed prerequisites to `assumption-testing`, and actual method-shape mechanics to `ssrf`/its `get-to-post` pack. Reachability or a 200 alone does not prove an action or privilege.
- **Sensitive files and data paths:** Could the fetcher access a specific internal page, configuration/export endpoint, artifact, or supported local-file scheme evidenced by the application? A path named in code is a lead, not proof the fetcher can read it. Distinguish an HTTP response, a job artifact or error that actually exposes content, and a blind request with no response sink. Confirm only enough allowed content to establish the boundary; keep third-party data and live secrets out of shared findings. Do not turn a file-read hypothesis into broad host-file collection.
- **Chaining:** If a reachable service has a separate auth, object, or workflow flaw, prove each link under its specialist and existing account/program policies. Different independently validated root causes may get linked findings; an imagined downstream use of a disclosed token is not a verified takeover. In a blind SSRF, use attributable owned callbacks, permitted side effects, or job artifacts for proof; do not infer a sensitive read from network contact.

For each ranked path, record the observed stack clue, proposed destination and ownership/scope, exact fetch capability needed, reachable or tested-negative boundary, visibility of returned data, and independently verified protected effect. Take the next discriminator only under `general-security-testing-policy` → `live-testing-policy` and the program's rules, at a rate that matches fetcher cost. Follow `information-disclosure-policy` for minimal restricted evidence of sensitive exposure; disclosure alone does not authorize credential use. Check effect and cleanup for owned writes before claiming control. Stop on out-of-scope destinations, instability, uncontrolled enumeration, non-owned mutation, or a sufficiently proven consequence. Update the **same FID** and `EVIDENCE.md` with proven links and exact limitations; hand untested hypotheses and useful app gadgets to their existing stores. `bunny-report-and-triage` remains report-only.
