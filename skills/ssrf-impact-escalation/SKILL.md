# SSRF Impact Escalation

**Boundary:** `ssrf` owns finding the fetch sink, characterizing its request/filter/response behavior, and pursuing enough internal reach or consequence to justify the *initial* finding. A public callback alone remains a fetch signal, not a demonstrated internal security boundary. Capture that first defensible finding with an FID without waiting for a dramatic chain. Then load this overlay through `impact-escalation` to ask what the **already-demonstrated primitive** means for this particular application. This is a non-exhaustive set of impact ideas, not a second discovery playbook, a destination checklist, payload recipes, or authority to probe. Extend it with observed app features, roles, trust relationships, and targeted MapStore gadgets; do not stop merely because none of the examples fit.

## Application clue → potential advantage → proof

- **Environment and identity:** Which component actually fetches—the API server, worker, image/PDF renderer, browser, or integration service? Does it carry a service identity, configured Authorization header, local-network privilege, or separate role? Which documented service or workflow trusts that identity or network location? A cloud logo, framework header, or another worker's behavior is only a clue. Route uncertain provider/runtime prerequisites to `technology-research`; do not import a public case's topology or severity.
- **Internal reads and sensitive files:** Which *specific* internal page, app API, configuration/export artifact, or supported file source would expose data the starting principal cannot read? Match it to what this fetcher returns: raw bytes, selected JSON keys, title, image pixels, error text, job artifact, or nothing. A service response may be reachable yet stripped by a decoder or cache; a renderer may introduce a distinct secondary fetch or output channel, but prove that transition. Compare owned positive/negative controls before treating a status/timing difference as a read. A path found in code is a lead, not file disclosure.
- **Platform capabilities:** If the observed runtime makes cloud metadata, task identity, a cluster API, or a container service relevant, ask what protected capability would actually become visible or usable. AWS EC2 IMDSv2 requires a token acquisition request and header; a GET-only fetcher does not thereby demonstrate that chain. GCP and Azure have their own header/version prerequisites; EC2 and ECS are different environments. For request-shape details, metadata taxonomy, URL bypasses, or protocols, go to `ssrf`'s matching technique pack and `headers`, not a duplicated recipe here. Reaching a metadata host, exposing a token-shaped value, and proving its permissions are different claims; disclosure does not authorize credential use.
- **Internal actions and chaining:** Could a named internal API, admin flow, queue, webhook, or proxy accept an action unavailable to the attacker? What method/body/header or service privilege must the *actual* fetcher supply? For a proposed write, select an owned target and require independent read-back of changed state; a 200, redirect, or queued job alone does not prove control. Route method mechanics to `ssrf`/its `get-to-post` pack and claimed auth/workflow guards to `assumption-testing`. A second flaw needs its own specialist and, if independently validated, a linked finding—not a presumed takeover.

For each promising path, name the observed clue, boundary, missing links, permitted discriminator, visible response or independent effect, and strongest benign explanation. Separate server-origin fetch and internal reach from two possible consequences: **read** through a verified output channel, or **action** through an attributable independent state/effect observation even when the fetch is blind. Then assess any authenticated authority and business consequence; no rung follows automatically from another. Use `general-security-testing-policy` → `live-testing-policy` and program, account, Attempts, and side-effect rules for any live step. Follow `information-disclosure-policy` for restricted minimal sensitive-data evidence; do not put live secrets or third-party content in shareable findings. Stop on out-of-scope reach, instability, uncontrolled enumeration, non-owned mutation, or sufficient proof—not on exhaustion of these idea prompts. Update the **same FID** and `EVIDENCE.md` with proved links and exact limitations; place untested branches in the Hypothesis Ledger and app gadgets in MapStore. `bunny-report-and-triage` remains report-only.
