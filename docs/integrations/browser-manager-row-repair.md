## Contract

Read-only `--program neon --account blue` plan selects the exact pair; apply requires the same pair, fresh plan hash, private backup directory and explicit owner-terminal confirmation. Other same-program accounts never enter the plan or update. The plan reports each eligible hashed row as `complete`, `sparse` or `missing` receipt evidence; this is an evidence classification, **not** a runtime safety claim. The immutable shift signature, canonical lease ID plus exact program/account/domain/agent/run/purpose/profile agreement, generated browser unit and canonical manager-directory launch filename establish identity. A non-null canonical service unit must match; a released canonical row with NULL service unit is supported because normal release clears it, but the reconstructed manager unit must still match `browser-<browser_id>` and any receipt `unit`/`service_unit` must agree. The canonical lease must be **released**, profile directory must exist and not be a symlink, and no *other active* canonical lease may hold that profile. Expired history does not masquerade as a live competing owner; its own row remains quarantined even when it shares the path. Active and expired records are never candidates regardless of receipt. A receipt may be missing or sparse historically; any field it *does* contain must agree. Invalid, symlinked, conflicting or malformed receipts are quarantined, not ignored.

At apply, every candidate additionally requires exact browser unit and watcher `inactive` (not an unavailable systemd result), terminal owner/root where identities exist, no profile SingletonLock, no profile process or receipt PID in a readable `/proc` scan, and only a definitively refused local CDP connection if an endpoint was recorded. A timeout, permission failure, connected port, unreadable process command line, or uncertain owner blocks the row. Missing historical owner/root identities are **not** treated as terminal identities: the independent systemd/profile/process checks are required instead. External owner/startup quiescence remains an operational prerequisite because these checks are not a cross-process atomic guarantee. No profile or owner mutation occurs.

Partial repair is allowed: a fresh offline plan hashes the eligible candidate set, apply independently rechecks live eligibility and refuses if that set changed; quarantined rows remain untouched and reported as hashed IDs/reasons. The apply result reports only actual updated count, not a claim that the whole history is safe. **Do not open migration** until all necessary historical records are reconciled separately, including blocked active/expired rows; this utility does not enable migration. Manager update uses conditional old-row values under node lock and attached SQLite transaction. `BEGIN IMMEDIATE` reserves both attached SQLite databases **before** either backup: even canonical writers that do not honor the node lock cannot commit between snapshots; locks are held through the manager update. Each attempt snapshots a fresh private manager+lease pair before mutation, removes both if either snapshot fails, rolls back and releases locks, and leaves successful pairs intact after transaction failure for recovery; retries use new names. This assumes ordinary SQLite writers on the same database files; replacing database files or writing around SQLite remains outside the transaction and requires the stated service/startup quiescence gate.
