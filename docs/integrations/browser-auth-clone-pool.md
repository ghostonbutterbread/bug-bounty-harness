## Implemented boundaries

The program-scoped `single`/`multiple` policy is stored by exact program with categorical evidence and CLI set/show readback. Its common admission predicate covers provisioner selection and canonical acquire/transfer: program `single` dominates exact-account `multiple`; exact-account/domain `single` dominates program `multiple`; unknown/absent program mode preserves the legacy exact-account behavior. The policy does not turn an unauthenticated browser into a clone and does not silently broaden another program/domain/account. Active leases are not changed by policy writes; logout remains passive evidence, not a switch to `multiple`.

The canonical private transfer identity/grant tables default to **no attestation** for existing rows. Manager attestation does not issue production grants. `manager_fixture_auth_transfer` is a private Python fixture transaction, not a CLI/HTTP/general account endpoint. It accepts only manager-derived owners matching exact `(fixture, fixture.invalid, anon)` and an exact loopback `http://localhost:<port>` origin, with a manager-selected fixture `/me` DOM principal check, one `__Host-` HttpOnly cookie, and one selected-origin localStorage key. It refuses mismatched owners, program, domain, account, origin, physical profiles, process/unit and CDP identities. Source and destination use separate live Chrome profiles. Exclusive adapter tickets and a quarantine/commit/activate sequence fence public CDP across transfer and uncertain replies; exact destination disposal is attempted when the end/commit outcome is uncertain. A failed exact stop remains `destination-cleanup-incomplete` and requires operator disposal; no source stop or raw profile copying. No caller-provided identity, auth payload, script, or site definition is accepted. No pool generation, peer promotion, or production site adapter is implemented.

The source is never stopped to resolve begin uncertainty.
