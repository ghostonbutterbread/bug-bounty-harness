## Implemented boundaries

The program-scoped `single`/`multiple` policy is stored by exact program with categorical evidence and CLI set/show readback. Its common admission predicate covers provisioner selection and canonical acquire/transfer: program `single` dominates exact-account `multiple`; exact-account/domain `single` dominates program `multiple`; unknown/absent program mode preserves the legacy exact-account behavior. The policy does not turn an unauthenticated browser into a clone and does not silently broaden another program/domain/account. Active leases are not changed by policy writes; logout remains passive evidence, not a switch to `multiple`.

The canonical private transfer identity/grant tables default to **no attestation** for existing rows. Manager attestation does not issue production grants. `manager_fixture_auth_transfer` is a private Python fixture transaction, not a CLI/HTTP/general account endpoint. It accepts only manager-derived owners matching exact `(fixture, fixture.invalid, anon)` and an exact loopback `http://127.0.0.1:<port>` origin, with a fixed fixture `/whoami` principal check, one HttpOnly cookie, and one selected-origin localStorage key. It refuses mismatched owners, program, domain, account, origin, physical profiles, process/unit and CDP identities. Source and destination use separate live Chrome profiles. Exclusive adapter tickets and a quarantine/commit/activate sequence fence public CDP before activation; exact destination disposal is attempted when the outcome is uncertain. After activation may have applied, failed exact stop is a terminal cleanup-incomplete state with **possible public exposure** requiring operator disposal; no source stop or raw profile copying. No caller-provided identity, auth payload, script, or site definition is accepted. No pool generation, peer promotion, or production site adapter is implemented.

Git reported no textual conflicts; semantic overlap in `browser_profile_lease.py` and `browser_provisioner.py` was checked with the combined suites. The independent review then reproduced an applied source begin whose reply was lost: the manager had no ticket to release and stranded the source public CDP. The repair supplies a manager-generated private transaction identifier tied to exact owner lease and original CDP generation, idempotent begin replay, and ticket/transaction/owner/generation matching for every privileged operation. A recovered begin is explicitly released without importing any auth; double failure returns a side-specific cleanup-incomplete status unless exact adapter identity proves it available. The source is never stopped to resolve begin uncertainty.

The next review found that after an import, an applied source `/transfer/end` with lost reply and unprovable release returned `source-cleanup-incomplete` before destination disposal. The candidate repair resolves source identity first, then attempts exact recorded destination stop before returning. `stop_recorded` checks recorded unit invocation and verifies unit inactivity, process-root terminal state and old CDP unavailability; failed or unproved stops remain `cleanup-incomplete`. The source is never stopped or claimed released when its identity probe cannot prove release. The response reports sanitized source and destination dispositions without a CDP URL or auth data. Post-import source recheck failures also keep the recipient private until exact disposal, instead of aborting it back to public CDP. The unproved source path cannot commit/activate the recipient.

The follow-up transaction boundary holds the manager/canonical locks through an outer `finally`: any escaping post-import `BaseException` (including cancellation during source end or recheck) attempts exact recorded destination disposal before propagation. The original exception is not swallowed; a sanitized exception note distinguishes verified disposal from `destination=cleanup-incomplete`, conservatively marks source release unverified, and never exposes auth or CDP URLs. The destination's old public URL remains quarantined/fenced pending verified stop. The deterministic failed-stop clock now allows one real `stopped()` poll and asserts unit, process-root, and CDP verification reach their applicable gates; earlier green failed-stop cases did not exercise those checks.

The pre-import begin interruption repair records the manager-generated `(transaction, owner lease, original CDP generation)` before the first adapter request and replays exactly that begin once even for `KeyboardInterrupt`, `SystemExit`, or `CancelledError`. It uses only the exact returned ticket to end a source or abort an empty destination. When replay fails, the manager probes exact adapter process/CDP identity and availability; no ticket is guessed, no other owner's transfer is ended, and an unproved source remains owned but fenced for explicit recovery. The original cancellation propagates with a sanitized `source=`/`destination=` disposition note (`cleanup-incomplete` when release cannot be proved). An interruption in `finally` cannot replace an already pending cancellation. Imported-recipient disposal remains the separate outer boundary, not a destination abort after auth import.

**Terminal publication boundary:** before `/activate` has applied, the recipient remains adapter-quarantined even though the rotated URL has been written to the private launch record and canonical lease; interruption propagates after one exact destination stop attempt, with a sanitized `disposed` or `cleanup-incomplete` note (the latter is not proof of disposal). A successful `activated: true` ACK is an irreversible committed marker: no later exception handler may interpret activation as cancellation rollback. If that ACK is lost or cancellation occurs inside the call, the manager accepts commitment only on exact adapter `available=true`, `quarantined=false`, process identity and rotated URL readback **plus** matching private launch record and canonical active owner/manager/URL. Verified applied activation returns `fixture-auth-transferred` even when the HTTP reply was lost or an interrupt arose after the adapter applied it; it does not stop the published recipient. An unverified activation attempts exact disposal and never claims success. The source owner is never disposed. This is a synchronous in-process boundary, not a crash-recovery journal; process death between canonical publication and activation leaves the adapter quarantined and requires operator reconciliation/disposal. The legacy broad post-import `finally` remains only for pre-commit failures and cannot override a committed state.

**Readback/disposal exception precedence:** an interrupt in activation identity readback is unverified evidence, not a replacement for an original pre-commit cancellation or proof of commitment. One exact recipient stop attempt is recorded before calling `stop_recorded`; a secondary `BaseException` from that attempt is treated as unverified disposal, so outer cleanup does not retry an unknown side effect. With an original interruption, that interruption wins; without one, a non-transport readback `BaseException` wins over a subsequent stop exception, or the stop exception propagates if readback had no such fault. Only a verified `True` stop may be called `disposed`. Notes carry sanitized source/destination dispositions; after `/activate` was attempted, they also mark `public-exposure=possible`. The adapter clears quarantine and ticket at activation, so an applied activation with lost ACK and failed identity readback cannot safely be rolled back with the old ticket. If exact stop fails, a normal transport-fault path returns `fixture-auth-transfer-terminal-uncertain` with `public_exposure=possible`, **not** `auth-clone-unavailable`; an escaping `BaseException` bears the same warning in its note. The published recipient may remain public until operator disposal. A verified stop proves current disposal, not absence of earlier public exposure. No source stop or unsafe rollback of a published recipient is attempted.
