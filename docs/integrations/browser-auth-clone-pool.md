## Implemented boundaries

The program-scoped `single`/`multiple` policy is stored by exact program with categorical evidence and CLI set/show readback. Its common admission predicate covers provisioner selection and canonical acquire/transfer: program `single` dominates exact-account `multiple`; exact-account/domain `single` dominates program `multiple`; unknown/absent program mode preserves the legacy exact-account behavior. The policy does not turn an unauthenticated browser into a clone and does not silently broaden another program/domain/account. Active leases are not changed by policy writes; logout remains passive evidence, not a switch to `multiple`.

The canonical private transfer identity/grant tables default to **no attestation** for existing rows. Manager attestation does not issue production grants. `manager_fixture_auth_transfer` is a private Python fixture transaction, not a CLI/HTTP/general account endpoint. It accepts only manager-derived owners matching exact `(fixture, fixture.invalid, anon)` and an exact loopback `http://127.0.0.1:<port>` origin, with a fixed fixture `/whoami` principal check, one HttpOnly cookie, and one selected-origin localStorage key. It refuses mismatched owners, program, domain, account, origin, physical profiles, process/unit and CDP identities. Source and destination use separate live Chrome profiles. Exclusive adapter tickets and a quarantine/commit/activate sequence fence public CDP before activation; exact destination disposal is attempted when the outcome is uncertain. After activation may have applied, failed readback triggers an exact ticket-bound adapter fence before exact stop: it rotates the public generation, quarantines admission, closes established clients and waits for detach/CDP barrier under the transfer lock. Failed stop is acceptable only with a verified fence; unproved fence plus failed stop remains terminal-uncertain and **blocks fixture approval**. Earlier exposure before recovery remains possible. No source stop or raw profile copying. No caller-provided identity, auth payload, script, or site definition is accepted. No pool generation, peer promotion, or production site adapter is implemented.

The next review found that after an import, an applied source `/transfer/end` with lost reply and unprovable release returned `source-cleanup-incomplete` before destination disposal. The candidate repair resolves source identity first, then attempts exact recorded destination stop before returning. `stop_recorded` checks recorded unit invocation and verifies unit inactivity, process-root terminal state and old CDP unavailability; failed or unproved stops remain `cleanup-incomplete`. The source is never stopped or claimed released when its identity probe cannot prove release. The response reports sanitized source and destination dispositions without a CDP URL or auth data. Post-import source recheck failures also keep the recipient private until exact disposal, instead of aborting it back to public CDP. The unproved source path cannot commit/activate the recipient.

The follow-up transaction boundary holds the manager/canonical locks through an outer `finally`: any escaping post-import `BaseException` (including cancellation during source end or recheck) attempts exact recorded destination disposal before propagation. The original exception is not swallowed; a sanitized exception note distinguishes verified disposal from `destination=cleanup-incomplete`, conservatively marks source release unverified, and never exposes auth or CDP URLs. The destination's old public URL remains quarantined/fenced pending verified stop. The deterministic failed-stop clock now allows one real `stopped()` poll and asserts unit, process-root, and CDP verification reach their applicable gates; earlier green failed-stop cases did not exercise those checks.

The pre-import begin interruption repair records the manager-generated `(transaction, owner lease, original CDP generation)` before the first adapter request and replays exactly that begin once even for `KeyboardInterrupt`, `SystemExit`, or `CancelledError`. It uses only the exact returned ticket to end a source or abort an empty destination. When replay fails, the manager probes exact adapter process/CDP identity and availability; no ticket is guessed, no other owner's transfer is ended, and an unproved source remains owned but fenced for explicit recovery. The original cancellation propagates with a sanitized `source=`/`destination=` disposition note (`cleanup-incomplete` when release cannot be proved). An interruption in `finally` cannot replace an already pending cancellation. Imported-recipient disposal remains the separate outer boundary, not a destination abort after auth import.

**Terminal publication boundary:** before `/activate` has applied, the recipient remains adapter-quarantined even though the rotated URL is in launch/canonical state. An activate ACK alone is not commitment evidence. A private `/transfer/status` bound to exact ticket, transaction, owner and original generation reports `activated` while `/identity.available` remains false (manager busy); independent identity, live process/unit, public rotated URL, launch and canonical owner readback must all match. The manager then finalizes the ticket and verifies `finalized` with the same independent readback; a lost finalize ACK is recoverable from the ticket-bound terminal receipt. If either proof fails, exact fence and recorded disposal remain required, with terminal uncertainty when neither is verified. The source owner is never disposed. This is synchronous in-process recovery, not a crash journal; process death between canonical publication and activation leaves the adapter quarantined.

**Readback/disposal exception precedence:** an interrupt in activation identity readback is unverified evidence, not a replacement for an original pre-commit cancellation or proof of commitment. One exact recipient stop attempt is recorded before calling `stop_recorded`; a secondary `BaseException` from that attempt is treated as unverified disposal, so outer cleanup does not retry an unknown side effect. With an original interruption, that interruption wins; without one, a non-transport readback `BaseException` wins over a subsequent stop exception, or the stop exception propagates if readback had no such fault. Only a verified `True` stop may be called `disposed`. Notes carry sanitized source/destination dispositions; after `/activate` was attempted, they mark `public-exposure=possible` and `public-fence=verified|unverified`. The adapter retains the exact transaction/owner/original generation/ticket across activation; the manager finalizes it only after exact activated readback. If activation or finalization cannot be proved, bounded exact fence retries precede disposal. A verified fence with failed stop reports a fenced, private, incomplete recipient (not a successful transfer); an unproved fence plus failed stop reports `fixture-auth-transfer-terminal-uncertain` with `public_exposure=possible` and blocks approval. A verified stop proves current disposal, not absence of earlier public exposure. No source stop or unsafe rollback of a published recipient is attempted. This is still synchronous recovery, not a crash journal.
