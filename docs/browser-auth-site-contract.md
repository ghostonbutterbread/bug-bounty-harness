# Browser auth site contract (manager-only transfer primitive)

The operator supplies one private JSON file per exact `(program, auth_domain, account_alias)` pool. The manager—not an agent or browser page—selects its path and expected pool identity. Use a root- or manager-owned regular file with mode `0600` in a manager-exclusive directory (no symlinked path; no unprotected group/world-writable ancestors). The loader opens each parent directory by file descriptor and opens the file relative to the pinned parent, rejecting symlinks and unsafe modes; this prevents a parent pathname swap from redirecting the read. It **does not** isolate against a process running as the same UID that can mutate the private directory/file. The manager must keep that directory and its contents outside agent-writable storage. Do not put this file in the repository or a run artifact. The file contains selectors and an expected principal, **not** cookies, tokens, passwords, or executable code.

Disposable offline fixture example, *not* a live-site authorization:

```json
{
  "program": "fixture",
  "auth_domain": "fixture.invalid",
  "account_alias": "anon",
  "disposable_fixture": true,
  "allowed_origins": ["http://localhost:8765"],
  "check": {
    "url": "http://localhost:8765/me",
    "method": "GET",
    "principal_selector": "[data-testid=\"account-name\"]",
    "expected_principal": "anon"
  },
  "local_storage_keys": ["fixture-credential"],
  "cookie_selector": {"name": "__Host-session", "domain": "localhost", "path": "/"}
}
```

`agents.browser_auth_site_contract.load_site_contract(path, *, program, auth_domain, account_alias, origin)` returns an immutable `SiteContract` only on exact pool and allowlisted canonical origin match. Explicit default ports (`:443` for HTTPS, `:80` for HTTP) are refused rather than treated as distinct aliases; nondefault ports remain exact. HTTPS is required except `http://localhost` for precisely the disposable fixture pool above. Check URL must be on the selected origin, without a query or fragment; only GET and an exact nonblank expected principal are supported. The closed `check` schema requires **exactly one** of `principal_selector` (legacy `#id` or `[data-testid="name"]` HTML element text) or `principal_json_key` (one simple top-level JSON object key matching `[A-Za-z][A-Za-z0-9_-]*`, such as `id`). For JSON, omit `principal_selector`; for HTML, omit `principal_json_key`. The fixed browser-side code parses the response JSON and accepts only an own, string-valued field at that key—no nested paths, arrays, coercion or whitespace trimming. Missing, malformed, null, nonstring or unequal values refuse; response bodies are not logged. `verify_check_response(contract, *, response_url, status, redirected, principal)` requires status 200, exact response URL, no redirect, and exact principal equality. Positive source/recipient browser-side `fetch` checks use `redirect: 'manual'` and `credentials: 'same-origin'`; the manager-only initial recipient's negative check uses `credentials: 'omit'` after emptiness preflight (below). No caller-supplied principal text alone is evidence of a real browser check. The loader/validator themselves make no request and do not enable auth transfer.

The schema is closed. Missing/extra keys, wildcard domains, free-form JavaScript, alternate storage types, unselected cookies, extra cookie attributes, or a check requiring redirects are unsupported and refused rather than guessed. Cookie selection is an exact `(name, domain, path)` for the selected origin host; localStorage is an explicit list of exact keys. Production cookie hosts must be multi-label, nonnumeric DNS names and cannot be one of the bounded common two-label suffixes in the loader (for example `co.uk` or `com.au`). This is **not** a public-suffix database or proof of registrability: operator review and the actual browser state gate remain required. In the **legacy selected-cookie mode**, inspect authoritative host-only metadata when available. CDP `Network.getAllCookies` does not expose that metadata: the only supported missing-metadata proof for this mode is a browser-enforced `__Host-` cookie with `Secure`, `Path=/`, and the exact origin hostname. Non-prefixed cookies and a `Domain`-scoped cookie fail closed in selected-cookie mode even if their displayed domain looks exact; do not infer host-only from a leading dot convention. The separate exact-origin mode below deliberately narrows such cookies and does not change this legacy boundary. Public `SiteContractError` text never includes raw JSON values or file paths. No real site contract is supplied by this change.

The private fixture integration reads only the manager-selected `fixture-site-contract.json` under the manager state directory, mode 0600 and outside agent-writable storage. It remains hard-fenced to `(fixture, fixture.invalid, anon)` and `http://localhost:<port>` with `__Host-session` and `fixture-credential`; no path, script, or check key is accepted from the agent. Its legacy HTML check uses a fixed browser-side `fetch` with `redirect: manual`, parses the returned HTML with `DOMParser`, extracts the selected element text, and requires exact URL/status/principal. The JSON alternative is also fixed browser-side code, not an agent-provided script. The example port above illustrates schema only; the runnable fixture canary uses a disposable ephemeral port.

The separate `browser_provisioner.manager_approved_auth_transfer(source_lease_id, destination_lease_id, *, origin, source_owner_agent_id, source_owner_run_id, destination_owner_agent_id, destination_owner_run_id)` is a **manager-process-only** synchronous initial empty-recipient operation, not an agent-facing RPC or a login service. Owner arguments are assertions against both authoritative rows, not credentials. The manager derives the exact shared `(program, auth_domain, account)` from its own and canonical lease records. The only production contract location is `<BROWSER_PROVISIONER_STATE parent>/auth-site-contracts/<sha256>.json`, where the filename is SHA-256 of `json.dumps((program, auth_domain, account), separators=(',', ':'), ensure_ascii=True).encode()`; no caller-supplied path is accepted. Provision this manager-exclusive directory at mode 0700 and each reviewed per-pool JSON file at mode 0600, outside agent-writable paths. As with the loader above, same-UID malicious writers are not isolated by POSIX modes; access control of the manager process/state must be enforced by the operator.

The approved operation accepts exact canonical HTTPS origins from a non-fixture contract, requires distinct live manager-owned profiles and leases in one pool, no effective `single` policy, and an empty destination origin (no localStorage or sessionStorage keys or cookies reaching its hostname). It checks zero storage and no origin-applicable cookies **before** the initial negative app check, executes only that negative check with `credentials: 'omit'` to avoid transmitting credentials or accepting anonymous `Set-Cookie`, and rechecks zero storage and no applicable cookies **after** the check; a pre-existing authenticated or populated recipient refuses without a negative fetch. In the legacy selected-cookie configuration it requires one selected host-only/`__Host-` Secure HttpOnly cookie and all explicitly selected nonempty localStorage values; exact-origin mode is described below. Positive browser-native, no-follow same-origin GET principal checks run independently in source and recipient after import; the source principal and URL are rechecked after import, and its original adapter identity/availability is read after release before recipient publication. Fixture HTML behavior remains unchanged. Existing exclusive ticket, generation, rollback, quarantine, exact disposal, finalization and public endpoint readback remain shared with the fixture operation. A public `auth-transferred` receipt is returned only after these checks. It is **not** a grant or a persistent auth generation, peer synchronization, proof of ongoing server-side session validity, or evidence for any real account. IndexedDB, sessionStorage, service-worker, passkey/device-bound and alternate cookie/store workflows are not supported. The selected site must be individually reviewed before invoking the primitive, and a real authorized account/browser cohort plus activation review remains separate. The opt-in `.test` HTTPS canary exercises two disposable managed Chromes through a localhost-only rejecting proxy; it sends no program-target traffic.

An alternative reviewed production contract uses `"state_mode": "exact-origin"` **instead of** both `cookie_selector` and `local_storage_keys`; all other fields (including the exact HTTPS `allowed_origins` and same-origin native `check`) remain required. For example, use the existing JSON structure above with `disposable_fixture: false`, a real reviewed pool and canonical `https://auth.example.test` origin/check URL, replacing those two selection fields with `"state_mode": "exact-origin"`. The disposable fixture contract cannot select this mode. This remains the same manager-only Python function/signature and fenced initial empty-recipient transaction; the caller cannot supply cookie or storage values. This mode copies **all provably applicable cookies** for the requested origin host, across paths, including a `__Host-` host-only cookie and explicitly domain-scoped parent-domain cookies, plus every origin localStorage entry (including when there are zero). It copies no cookies for unrelated domains and never copies another origin's storage. Maximum inventory: 256 browser cookies, 32 applicable cookies totaling at most 131072 UTF-8 bytes, 64 localStorage entries totaling at most 65536 UTF-8 bytes; at least one applicable cookie is required. The source and recipient must have zero sessionStorage entries; the recipient must also have zero localStorage entries and no cookie reaching the origin. Both browsers must pass the native principal check independently after import; the source principal, page URL, cookies and localStorage are rechecked unchanged before publication.

CDP `Network.getAllCookies` does **not** prove an arbitrary exact-host cookie is host-only. In **exact-origin mode**, a cookie displayed at the reviewed origin host (plain or leading-dot representation), including an unprefixed one without `hostOnly` metadata, is proven *applicable* to that host but not proven host-only. The recipient is deliberately narrower: `Network.setCookies` receives the exact HTTPS origin URL and **no Domain**, so even an exact-host Domain-scoped source cookie becomes host-only. The destination's attributes are read back, and `Network.getCookies` at a child hostname must not expose any selected host-only name/path. Contradictory `__Host-`/hostOnly metadata still refuses. A strict parent-domain cookie is supported only when the browser represents it with a leading-dot Domain scope or authoritative `hostOnly: false`; an unmarked parent string might be an unrelated host-only cookie and is refused. Parent cookies receive explicit Domain. Source cookies with the same name/path across scopes (including exact-host and parent), or exact duplicates, refuse before import rather than overwriting or ambiguously comparing the recipient. Path, Secure, HttpOnly, SameSite, priority, source scheme/port when present, and persistent expiry are preserved (session cookies remain session cookies). Partition keys, opaque partitions, SameParty cookies, unknown source schemes, ambiguous scopes, unsupported attributes and ambiguous stores are refused rather than claimed transferred. Source and recipient cookie attributes and storage are read back; after an imported recipient's positive check fails or raises, the manager still rechecks source principal, URL, raw selected cookies and origin storage before deciding rollback. A generic rollback is clean only when destination origin-applicable cookies, all localStorage and all sessionStorage are empty; otherwise the exact recipient is disposed and cleanup uncertainty is reported. Review the actual site's cookie/store inventory, domain scope, server session policy, and principal check before supplying a contract; IndexedDB, service workers, passkeys/device binding and third-party cross-origin state are **not** copied. Offline JSON checks do not constitute a real-site manager-transfer proof. This contract mode provides no agent RPC or selected-runtime activation.
