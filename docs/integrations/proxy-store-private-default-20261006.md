# Proxy Store private creation defaults

- **Feature branch:** `fix/proxy-store-private-default-20261006` (based on `origin/beta` at `59e72403600c9e9035081ca32e7ac5c64f3bbd83`).
- **Scope:** `skills/chromium-test/scripts/proxy_store.py` and `agents/test_proxy_store.py`; no captured packets accessed and no live target traffic.
- **Current defect:** In a synthetic store under umask `022`, SQLite created a database at `0644` and the dedicated directory at `0755`. The bounded, read-only selected-Hoster check found its *existing* database at `0600`, dedicated directory at `0755`, home at `0750`, and selected beta checkout clean at `bdce1f39cb277b43ccd7ee8e95fa2df35f1ae975`; this does not establish existing captured-data exposure. The fix prevents a recreated/default or explicitly chosen DB from inheriting permissive file bits.
- **Fix:** `connect` walks each path component using directory descriptors and `O_NOFOLLOW`, creates missing components at `0700`, and refuses intermediate symlinks before any chmod. Every ancestor and the final parent must be owned by the current UID or trusted root; otherwise an owner of a nominally `0755` directory could replace the next path component before SQLite reopens it. An ancestor writable by another account is rejected unless an earlier owner-only, non-traversable trusted directory fences it; a group/world-writable custom DB parent is always rejected. The default dedicated directory is tightened through its verified descriptor only; existing custom parent modes are untouched. The DB and existing `-wal`/`-shm` are opened relative to the checked directory without following final symlinks and tightened before SQLite opens them. New DB creation uses `0600`; SQLite-created WAL/SHM modes are tested under umask `022`, and sidecars present at connect time are rechecked after SQLite connects. Query, lanes, and export use SQLite `mode=ro`; a pre-existing `0444` DB remains read-only for the owner (`0400`) while query/export work.
